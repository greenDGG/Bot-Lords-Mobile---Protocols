# Proto 3125 - Cofre VIP (estado / rechazo)

## Descripción

El servidor envía `Proto=3125` en respuesta a `3126` (reclamo) o como notificación de estado.

Se observaron **dos formas** de cuerpo (672 muestras en 3 cuentas, 2026-09-01 → 09-27):

| byte[0] | Significado | Longitudes vistas |
|---------|-------------|-------------------|
| `0x00` | **Estado**: ranuras reclamadas (máscara) + timestamp del último reclamo | 20, 40, 45, 50, 55 B |
| `0x03` | **Reclamo rechazado**: la ranura pedida ya está reclamada (o no disponible) | siempre 20 B, `03 00 00 00 …` |

Correlación verificada: 298/298 rechazos correspondieron a pedir una ranura **ocupada**;
84 respuestas de estado correspondieron a pedir una ranura **libre**.

## Wire

| Proto | Wire | Cifrado |
|-------|------|---------|
| 3125 | `0x0C35` | plano |

## Payload - estado (`byte[0] == 0x00`)

| Offset | Tamaño | Campo | Descripción |
|--------|--------|-------|-------------|
| 0 | 1 (`u8`) | status | `0x00` = estado |
| 1 | 1 (`u8`) | mask (bits 0-7) | Máscara de bits: 1 = ranura reclamada, 0 = disponible |
| 2-5 | 4 (`uint32` LE) | lastClaimTimestamp | Timestamp Unix del último reclamo exitoso |
| 6+ | restante | desconocido | Datos adicionales sin decodificar |

La máscara es un `uint16` en **big-endian** en offset 0 (`status` = byte alto). En la
práctica `status` es siempre `0x00` para estados, por lo que la máscara efectiva es el
byte 1 (ranuras 0-7 observadas; se parsea como `readUInt16BE(0)` para no perder ranuras 8-9).

> **Cuidado:** leer la máscara como `uint16 LE` (interpretación previa) producía
> `0x0100`/`0x0500` en lugar de `0x0001`/`0x0005`, con lo que `nextIndex` salía
> **siempre 0** y el bot volvía a reclamar la ranura 0 ya reclamada.

## Payload - rechazo (`byte[0] != 0x00`)

```
03 00 00 00 <16 bytes no decodificados (basura/eco)>
```

- `byte[0] = 0x03` = reclamo rechazado.
- Los bytes 1-3 son `00 00 00` en 297/298 muestras (1 muestra con `03 7f 00 00`).
- Los bytes 4+ no siguen el layout del estado (timestamps basura: 0, junk, años 1970/1978/2095).

**El parser los ignora** (`parseVipChest()` devuelve `null`): si se interpretaran como
estado se calcularía un `nextClaim` basura (p. ej. época 1970 → "ya disponible") y el bot
entraba en **bucle de reintentos** (observado: 6 reclamos rechazados de la ranura 2 en 15 min).

## Máscara de bits

Cada bit representa una ranura (índices observados 0-2; se asume 0-9):

| Bit | Índice | Significado |
|-----|--------|-------------|
| 0 | 0 | Ranura 0 reclamada |
| 1 | 1 | Ranura 1 reclamada |
| 2 | 2 | Ranura 2 reclamada |
| ... | ... | ... |
| 9 | 9 | Ranura 9 reclamada |

- `0` = ranura **disponible** para reclamar
- `1` = ranura ya **reclamada**

`nextIndex` = primer bit en 0 (primera ranura libre); `-1` si no queda ninguna.

## Ejemplos reales

Estado (ranura 0 reclamada):

```
body = 00 01 c5 51 65 61 00 00 ...
```

| Campo | Bytes | Valor |
|-------|-------|-------|
| status | `00` | estado |
| mask | `01` | `0x0001` = bit 0 → ranura 0 reclamada |
| lastClaimTimestamp | `c5 51 65 61` | u32 LE |
| nextIndex | calculado | 1 (primera ranura libre) |

Rechazo:

```
body = 03 00 00 00 74 f8 3e 61 3c 01 00 00 ...
```

→ ranura pedida ya reclamada; **no** es estado (el ejemplo antiguo `03 00 00 00 …` con
"mask = 0x0003 → próximo índice 2" era erróneo: ese cuerpo es un rechazo).

## Relación con 3126

| Proto | Dirección | Uso |
|-------|-----------|-----|
| `3126` | Cliente → Servidor | Reclamar cofre VIP (envía índice de ranura) |
| `3125` | Servidor → Cliente | `00…` = estado actualizado; `03…` = reclamo rechazado |

**Flujo:**
1. Servidor envía `3125` con el estado actual (`00…`)
2. Bot calcula `nextIndex` (primer bit libre) y guarda `nextClaim = lastClaim + 3600`
3. Si `nextIndex != -1` y `Date.now() >= nextClaim * 1000`, envía `3126` con ese índice
4. Marca localmente la ranura (`mask |= 1 << idx`, `nextClaim = now + 3600`)
5. El `3125` de respuesta:
   - `00…` → pisar el estado con el del servidor
   - `03…` → **conservar** el estado local (ya quedó marcado el paso 4) y loguear el rechazo

## Uso en el bot

- `handlers/vip-chest.handler.ts` → `handleVipChest()` filtra rechazos (`isVipChestRejected`) y parsea estados con `parseVipChest()` (`models/vip-chest.types.ts`)
- Se guarda en `bot.vipChestMem`
- `actions/chest.action.ts` → `ChestVipAction` verifica:
  - `nextIndex != -1` (hay ranuras libres)
  - `Date.now() >= nextClaim * 1000` (pasó la hora de cooldown)
- Si ambas condiciones se cumplen, envía `3126` con el índice
- Tras enviar, actualiza localmente: `mask |= (1 << idx)`, `nextClaim = now + 3600`, recalcula `nextIndex`

## Cooldown

- Cada ranura tiene cooldown de **1 hora** (`VIP_CHEST_COOLDOWN = 3600`) después de reclamar
- Todas las ranuras se reinician diariamente al reinicio de la cuenta del servidor

## Pendientes de decodificar

- Contenido de los 16 bytes del rechazo
- `3126`: los 4 bytes previos al índice (`u32`, valores 15/19/22) — ver `3126.md`
