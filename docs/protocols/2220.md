# Proto 2220 - Datos del mapa (respuesta)

## Descripción

El servidor envía `Proto=2220` como respuesta a un `Proto=2201` (solicitud de datos del mapa). Contiene tiles con información de castillos, recursos, monstruos y terreno vacío. Puede llegar en un solo paquete grande o en múltiples paquetes de continuación.

También se usa para **updates de tiles** (cuerpos múltiplos de 62), para notificar **marchas en curso** (una caravana saliendo, etc.), para avisar el **HP nuevo de un monstruo tras un golpe de caza** y para decir **quién ocupa un tile de recurso y cuánto queda**. Ver [Formatos](#formatos-variantes-bajo-el-mismo-proto), [Variante march](#variante-march-marcha-visible-en-el-mapa), [Variante monster hit](#variante-monster-hit-hp-del-monstruo-tras-un-golpe) y [Variante ocupación de tile](#variante-ocupación-de-tile-record-0x03).

> **Convención de timestamps**: todo campo `uint32` de timestamp va seguido de **4 bytes en `00`**. No es un campo con significado, es relleno fijo del protocolo (aparece en `2453` offset 9-12, `2442` offset 8-11, y en la variante march offset 45-48).

## Formatos (variantes bajo el mismo proto)

`classifyMapBody(body)` (`backend/src/bot/models/map.types.ts`) decide cuál es **antes** de parsear:

| # | Formato | Cuerpo | Parser |
|---|---------|--------|--------|
| 1 | **Entrega** de mapa (respuesta a `2201`, primera tanda y continuaciones) | **> 1000 B** (cabecera + N×51 con N ≈ 10 por celda) | `parseMapPacket` |
| 2 | **Update** de tiles (un tile cambia/desaparece) | múltiplo de **62** y ≤ 1000 B → N × `[11B header][51B tile]` | `parse2220` |
| 3 | **Marcha** en curso | resto, ≥ 53 B y valida como marcha | `parseMapMarch` |
| 4 | **Monster hit** (HP del monstruo tras un golpe de caza) | 93..500 B, no múltiplo de 62 | `parseMonsterHit` — el handler lo intercepta **antes** de `classifyMapBody` |
| 5 | **Respuesta a `2202`** (consulta de tile: estado de reclamo de un cofre) | **60 B**, empieza con `0c` | `parseTileInfo` — también se intercepta **antes** de `classifyMapBody`, si no encajaría en la variante 3 y metería un registro inventado en `mapMarches` |
| 6 | **Ocupación de tile** (quién recolecta un tile de recurso + cantidad restante) | **48..176 B** con un record `03` cuyo u16 = 37 | `parseTileOccupants` — se intercepta **antes** de `classifyMapBody`; lo que sobra del body (p.ej. una marcha de 73 B) se re-procesa en recursión |

> **Regla observada**: lo que pasa de 1000 B es el mapa; lo pequeño es una actualización, una marcha, un golpe de caza o una ocupación de tile.

Por qué hace falta separarlos por **tamaño** y no solo por `len % 62`: hay entregas cuya
longitud resulta múltiplo de 62 — `45 + 21×51 = 1116`, `3 + 51×51 = 2604`,
`45 + 83×51 = 4278`, `15 + 7×51 = 372`. Con el dispatch antiguo (marcha → `parse2220` →
`parseMapPacket`) esas entregas las absorbía el parser de updates y se perdían los tiles,
porque `parseTileRecord` no puede fallar (`decodeCoordId` son operaciones bitwise que nunca
lanzan) y el handler hacía `return` sin llegar al fallback. El único caso pequeño es
`372`, y se resuelve con la comprobación de cabecera de eco (`15 + 7×51`) por debajo del umbral.

**Sin resolver**: el header de 11 B del formato 2 sigue sin descifrar, así que los formatos
2 y 3 solo se distinguen por tamaño. Ver `backend/scripts/test-2220-classify.ts`.

## Estructura general

El body de una **entrega** contiene una cabecera seguida de N registros de tiles de **51 bytes** cada uno.

### Tipos de cabecera

El tamaño de cabecera se detecta por la longitud del body (cuerpo = `Len - 4` del frame):

| Tipo | Tamaño | Cuándo |
|------|--------|--------|
| Continuación | 3 bytes | Paquetes adicionales sin eco de celdas |
| Eco de celdas | 3 + n×10 + 2 = **5 + n×10** (15/25/35/45/55/…/**95** con n=9) | Primer paquete tras 2201 con n celdas pedidas (n = count del 2201) |

```
[0..2]   prefijo 3B
[3..]    n × [uint16 cellIndex LE][u32][u32]   (10 bytes por celda)
[final]  2B (trailer)
→ tiles en 51 bytes desde offset = 3 + n×10 + 2 = 5 + n×10
```

Ejemplo real (count=4 → header 45): `16 c0 49 | b701… b801… c701… c801… | 333c` + tiles — las celdas `b701=439, b801=440, c701=455, c801=456` son exactamente las pedidas en el 2201.

Detección automática (`detectMapHeaderSize`): prueba candidatas `[3, 15, 25, 35, 45, 55, …, 5+40×10]` y usa la que divida exactamente `(len - h) % 51 === 0`, validando además que los n uint16 del eco sean índices de celda válidos (≤ 4095 = 16×256 − 1). Cabezas de tamaño `5 + n×10` difieren en múltiplos de 10, no múltiplos de 51, salvo **n=10** (5+100=105 ≡ 3 mod 51, ambiguo con la continuación de 3B) — ese n se excluye porque el bot solo pide tamaños `(2r+1)²` = 1, 4, 9, 16, 25…, nunca 10. Sin división exacta (tail parcial), elige la primera candidata cuyo primer record decodifique como coord válida.

> Bug corregido: antes solo se probaban 25 y 3; una respuesta con eco de 4 celdas (header 45) caía en fallback 25, desalineaba los 51-byte records y se perdían casi todos los tiles (provocaba "No se encontró tile del target tras 2201" en el flujo de supply). Luego se amplió a las cabeceras 15/25/35/45 y finalmente a `5+n×10` general para respuestas con eco de count=9 (5+9×10=95).

## Variante march (marcha visible en el mapa)

Es la variante 3 de [Formatos](#formatos-variantes-bajo-el-mismo-proto): cuerpo pequeño (≤ 1000 B), no múltiplo de 62 y que pasa las validaciones de `parseMapMarch`. Ej. caravana de supply saliendo. Ojo: la [variante monster hit](#variante-monster-hit-hp-del-monstruo-tras-un-golpe) también es pequeña y no múltiplo de 62, pero se intercepta antes de llegar aquí.

**El header no tiene longitud fija.** Tabla y ejemplo de abajo corresponden a la muestra de **73 B** (header de 17 B); en logs reales se ven además bodies de **85 B (header 29)**, **88 B (header 32)** y **103 B (header 47)**. El patrón del header es una lista de entradas `[9B id][payload…]` que termina siempre en `3e00` + coord de 6 B. Lo que sí es fijo es **la cola: 56 bytes desde el nombre hasta el final del body**, así que `parseMapMarch` prueba dos anclas: el nombre de la **primera** entrada (offset 17, la de 73 B) y, si falla, `len - 56`.

Un body también puede traer **varias marchas apiladas** (ej. 176 B = record de 73 + record de 103): `parseMapMarches()` las desapila recorriendo de a un record (nombre + 56). Los bodies de 73 B siguen siendo la mayoría (≈460 por día de log).

| Offset | Tamaño | Campo | Descripción |
|--------|--------|-------|-------------|
| 0-16 | 17 | header | **Sin descifrar** (ver desglose abajo) |
| 17-29 | 13 | name | Nombre del jugador (null-terminated, UTF-8) |
| 30-32 | 3 | guild | Tag del gremio (null-terminated) |
| 33-34 | 2 | kingdom | Reino (uint16 LE, `cf04` = 1231) |
| 35-37 | 3 | origin | Coordenada de origen (3 bytes) |
| 38-40 | 3 | destination | Coordenada de destino (3 bytes) |
| 41-44 | 4 | startTime | Inicio de la ida (uint32 LE, unix) |
| 45-48 | 4 | — | `00000000` — convención de timestamps (no es un campo) |
| 49-52 | 4 | duration | Duración de ida en segundos (uint32 LE) |
| 53-72 | 20 | datos | **Sin descifrar** — 5×uint32 LE = `0,0,N,0,0` |

Validaciones: `duration > 0 && duration < 30 días && startTime > 1_600_000_000`. La marcha se conserva en `bot.mapMarches` hasta `startTime + 2×duration` (idá + vuelta) — es lo que libera el slot de caravana.

### Header de 17 bytes (muestra de 73 B) — sin descifrar

```
[0]       0x0E
[1..2]    uint16 LE   4041 / 6555 (las 2 muestras)
[3..8]    6 bytes     00 00 00 00 00 00
[9..10]   uint16 LE   62
[11..12]  uint16 LE   156 / 62
[13..16]  uint32 LE   967198 / 721943 — cambia entre marchas (¿id de marcha?)
```

### Cola de 20 bytes — sin descifrar

5 × uint32 LE = `0, 0, N, 0, 0` con **N** variable (6, 7 en las muestras). El tamaño (20 B) coincide con las 5 cantidades de recursos del payload de [`2452`](2452.md), pero el valor no encaja con `maxAmount`.

## Variante monster hit (HP del monstruo tras un golpe)

Llega al atacante cuando su golpe de caza ([`2488`](2488.md)) aterriza. Trae el **HP nuevo
del monstruo** y los tiempos de **ida/vuelta** de la marcha. Cuerpo pequeño (muestra
confirmada: **104 bytes**), no múltiplo de 62 y con el bloque de marcha desplazado 31 B
respecto a la variante march (nombre en offset 48 en vez de 17).

| Offset | Tamaño | Campo | Descripción |
|--------|--------|-------|-------------|
| 0-8 | 9 | header | **Sin descifrar** |
| 9-11 | 3 | monsterCoord | Coordenada del monstruo |
| 12-15 | 4 | hp | HP nuevo (float32 LE, **0..100**) |
| 16-47 | 32 | header | **Sin descifrar** — repite el patrón `[1B][1B][7B ceros]` de la marcha |
| 48-60 | 13 | name | Nombre del atacante (null-terminated) |
| 61-63 | 3 | guild | Tag del gremio |
| 64-65 | 2 | kingdom | Reino (uint16 LE) |
| 66-68 | 3 | coordA | Ubicación A = **monstruo** (idénticos a 9-11) |
| 69-71 | 3 | coordB | Ubicación B = **atacante** |
| 72-75 | 4 | eventTime | Unix seconds del golpe |
| 76-79 | 4 | — | `00000000` — convención de timestamps |
| 80-83 | 4 | returnSeconds | Duración de la **vuelta** A→B en segundos |
| 84-87 | 4 | — | `00000000` |
| 88-103 | 16 | datos | **Sin descifrar** |

Validaciones (a prueba de falsos positivos): `hp ∈ [0,100]`, reino ≥ 100, `eventTime` en
rango, `returnSeconds ≤ 3600`, y **las coordenadas de 9-11 tienen que ser iguales a las de
66-68**.

### Uso en el bot

- Actualiza `mapTiles[coord].monster.hp` (el GUI pinta el HP nuevo sin pedir `2201`).
- Si coincide con `huntTarget`, suma `hitsLanded` y calcula
  `returnAt = ahora + returnSeconds` → el bucle espera ese instante antes del siguiente golpe.
- `hitsLanded` y `returnAt` viajan en el evento `huntUpdated`.
- Escala: los tiles guardan el HP en 0-100 o en 0-1 según la muestra; `matchHpScale()`
  reescala el valor nuevo a la escala que ya tiene el tile.

## Variante ocupación de tile (record 0x03)

Es la variante 6 de [Formatos](#formatos-variantes-bajo-el-mismo-proto). Dice **quién está en
una coordenada** y **cuánta cantidad le queda al tile**. En **todas** las muestras (34 records
en un día de log de 3 cuentas) la coord es un tile de recurso (types 1-5: Trigo, Piedra,
Mineral, Madera, Oro), o sea que el record es una *actualización de tile de recurso*:
**quién recolecta + restantes**. Nombre vacío = **nadie visible** recolectando (el tile sigue
perdiendo cantidad igual).

> **Bug que arregló este parser**: los cuerpos de **63 B** (`0f` 15 B + `03` 48 B) los tomaba
> `classifyMapBody` como `delivery`, `parseMapPacket` leía bytes aleatorios como tiles y
> metía **un tile fantasma en (64,0)** (log `[MAPA] Recibidos 1 tiles (0 nuevos…)`). Lo mismo
> pasaba con los de 78, 84 y 105 B. Los de 15/30/45 B no llegaban a molestar (devolvían
> `null`), y los de 88/103/176 B se parseaban bien como marcha.

### El body es una pila de records

Todos los records menos uno tienen el mismo layout:

```
[kind 1B][serial u32 LE][4B ceros][u16 LE tamaño][payload de `tamaño` bytes]
   1   +     4        +    4      +      2        +        tamaño
```

El único que **no** lleva el `u16` de tamaño es el `0x0f`, que es siempre **15 B**. El record
`0x03` lleva `u16 = 37` → mide `11 + 37 = 48` B. Longitudes de body observadas:
**63** (`0f`+`03`), **121/144/169** (1 a 3 records `03` apilados) y **78, 84, 105, 136, 142,
148, 151, 157** (un `0x3f`/`0x0f` adelante). Máximo visto: 176 B → el escáner sólo mira
cuerpos de **≤ 500 B** (nunca entregas).

### Campos del record `0x03` (48 B)

| Offset | Tamaño | Campo | Descripción |
|--------|--------|-------|-------------|
| 0 | 1 | kind | `03` |
| 1-4 | 4 | serial | uint32 LE auto-incremental del servidor |
| 5-8 | 4 | — | `00000000` |
| 9-10 | 2 | size | uint16 LE = **37** (constante: es la firma del record) |
| 11-13 | 3 | coord | Coordenada del tile (3 bytes, ver proto 2201) |
| 14-26 | 13 | name | Jugador en el tile (null-terminated) → **`''` = sin ocupante** |
| 27-29 | 3 | guild | Tag del gremio (null-terminated) |
| 30-31 | 2 | kingdom | Reino (uint16 LE) — 0 cuando no hay ocupante |
| 32-35 | 4 | **resourceAmount** | **Recursos restantes del tile** (uint32 LE) — **CONFIRMADO**: coincide al byte con `resource.amount` de las entregas (p.ej. `1575000` de un tile de Trigo fresco, `1484108` cuando queda poco; `10`/`50` en tiles a punto de agotarse) |
| 36-39 | 4 | unknownF32 | **Sin confirmar** (float32 LE). Escala compatible con *power o kills en millones* (0.12 … 403.79) y es **0 cuando no hay ocupante**, pero varía para algunos jugadores en pocos segundos |
| 40-43 | 4 | time | Unix seconds del update (uint32 LE) — 0 cuando no hay ocupante |
| 44-47 | 4 | — | `00000000` — **siempre** en 212/212 muestras (validación) |

**Validaciones** (a prueba de falsos positivos): `u16@9 == 37`, coord con `x,y ≤ 8191`,
gremio y nombre sin bytes de control, `tail == 0`. Con nombre → `100 ≤ kingdom ≤ 4000` y
`time ≥ 1_600_000_000`; **sin** nombre → `kingdom == 0 && time == 0 && f32 == 0`.

### Uso en el bot

- `bot.mapOccupants: Map<tileId, TileOccupant>` — último estado por tile (solo tiles con
  ocupante visible).
- `tile.occupiedBy` en `ParsedMapTile` (viaja al front en `mapDataUpdated`); si el tile ya
  estaba en `mapTiles`, también se le refresca `tile.resource.amount` con el valor nuevo.
- Log: `[MAPA] (223,565) ocupa I Love Ado [uFO] · k=1231 · rec=1555047 f32=245.06 · …` y
  `[MAPA] (223,565) sin ocupante · rec=1573090`. Sólo se loguea cuando cambia algo
  (nombre, gremio, reino, cantidad o f32); los repetidos idénticos se descartan.
- El handler intercepta **antes** de `classifyMapBody` y vuelve a llamar a sí mismo con lo
  que sobra del body, así no se pierde la marcha que viene detrás ni se crea el tile fantasma.

### Sin descifrar: el record `0x0f` (15 B)

```
[0] 0x0f · [1..4] serial u32 · [5..8] 4B ceros · [9..11] coord 3B · [12..14] 3B
```

Son ~460 por día de log y **nunca** coinciden con la coord del `0x03` que viene detrás
(p.ej. `0f`=(252,566) y `03`=(223,565)), así que **no se actúa sobre ellos**: semántica
desconocida y un clear erróneo borraría un ocupante real. Se documentan por completitud.

## Cada tile (registro de 51 bytes)

| Offset | Tamaño | Campo | Descripción |
|--------|--------|-------|-------------|
| 0-2 | 3 | coord | Coordenada codificada (3 bytes, ver proto 2201) |
| 3 | 1 | type | Tipo de tile (ver tabla de tipos abajo) |
| 4-50 | 47 | data | Datos específicos del tipo |

## Tipos de tile

### Type 0x01-0x05: Recursos (vetas)

| Offset | Tamaño | Campo | Descripción |
|--------|--------|-------|-------------|
| 3 | 1 | type | 1=Trigo, 2=Piedra, 3=Mineral, 4=Madera, 5=Oro |
| 22 | 1 | level | Nivel del recurso |
| 23-26 | 4 | amount | Cantidad (uint32 LE) |

```
[coord 3B][type 1B][18 ceros][nivel 1B][cantidad u32LE]
```

### Type 0x08: Castillo / nido de jugador

| Offset | Tamaño | Campo | Descripción |
|--------|--------|-------|-------------|
| 4-16 | 13 | name | Nombre del jugador (null-terminated, UTF-8) |
| 17-19 | 3 | guild | Tag del gremio (null-terminated) |
| 20-21 | 2 | kingdom | Reino (uint16 LE) |
| 22 | 1 | level | Nivel de la fortaleza |
| 23-24 | 2 | shield | Escudo activo (uint16 LE, 0 = no, otro = sí) |
| 28-29 | 2 | skin | Skin del castillo (2 bytes hex) |

```
[coord 3B][08 1B][nombre 13B][guild 3B][reino u16LE][nivel 1B][escudo u16LE][...][skin 2B]
```

Si el nombre contiene "dark" → es un castillo Darkness.

### Type 0x0A: Monstruo

| Offset | Tamaño | Campo | Descripción |
|--------|--------|-------|-------------|
| 4 | 1 | level | Nivel del monstruo |
| 5-10 | 6 | id | ID del monstruo (6 bytes, se muestra como hex) |
| 11-14 | 4 | hp | Porcentaje de HP (float32 LE, 0.0 - 1.0) |

```
[coord 3B][0a 1B][nivel 1B][id 6B][hp% float32LE]
```

### Otros types: Terreno vacío

Tiles con type distinto a 1-5, 8 y 0x0A se consideran vacíos. Se extraen nombre y guild tag si están presentes.

## Ejemplo de body completo

```
Primer paquete (2201 count=n → 2220):
[header (5 + n×10)B][tile1 51B]...[tileN 51B]
Body = (5 + n×10) + N×51 bytes     (n=4 → 45B; n=9 → 95B)

Continuación:
[header 3B][tile1 51B]...[tileN 51B]
Body = 3 + N×51 bytes
```

## Datos extraídos por tipo

### ParsedMapTile (interfaz)

```typescript
{
  id: number;          // ID del tile (3 bytes codificados)
  x: number;           // Coordenada X real (xi * 2 + paridad)
  y: number;           // Coordenada Y real (yi * 2 + paridad)
  type: number;        // Byte tipo (1-5 recurso, 8 castle, 0x0a monster)
  name: string;        // Nombre (jugador o recurso)
  guild: string;       // Tag de gremio
  empty: boolean;      // true si no es recurso/castle/monster
  resource?: {         // Solo types 1-5
    type: number;      // 1=Trigo, 2=Piedra, 3=Mineral, 4=Madera, 5=Oro
    level: number;     // Nivel del recurso
    amount: number;    // Cantidad disponible
  };
  monster?: {          // Solo type 0x0a
    level: number;
    id: string;        // 6 bytes como hex string
    hp: number;        // 0.0 - 1.0 (float32)
  };
  castle?: {           // Solo type 8
    kingdom: number;   // Reino (uint16)
    level: number;     // Nivel fortaleza
    darkness: boolean; // true si nombre contiene "dark"
    shield: boolean;   // escudo activo
    skin: string;      // 2 bytes hex
  };
  occupiedBy?: {       // Viaja en el push 0x03 (ver variante ocupación de tile)
    x: number; y: number; tileId: number;
    name: string;      // '' = sin ocupante
    guild: string; kingdom: number;
    resourceAmount: number; // recursos restantes del tile
    unknownF32: number;     // sin confirmar (0 si no hay ocupante)
    time: number; serial: number;
  };
  rawData: Buffer;     // 51 bytes originales del tile
}
```

## Almacenamiento

Los tiles se acumulan en un `Map<number, ParsedMapTile>` en `BotInstance.mapTiles` (key = tile ID). Al recibir un 2220, se actualizan solo tiles nuevos o modificados. Se emite evento `mapDataUpdated` al frontend.

Los **ocupantes de tiles de recurso** (push `0x03`) se acumulan aparte en `BotInstance.mapOccupants` (solo tiles con nombre) y se copian a `tile.occupiedBy` cuando el tile existe en `mapTiles`.
