# Análisis del Protocolo 1401 (Inventario)

## Resumen

El protocolo **1401** corresponde a la sincronización completa del **inventario del jugador**.

Su objetivo es transmitir al cliente todos los objetos que posee el jugador junto con la cantidad disponible de cada uno.

El cliente ya contiene internamente toda la información visual y descriptiva de los objetos:

- Nombre.
- Icono.
- Descripción.
- Rareza.
- Categoría.
- Información visual.

Por lo tanto, el servidor únicamente transmite:

- Identificador interno del objeto.
- Cantidad del objeto.

---

# Estructura general

El paquete está compuesto por una cabecera fija seguida de una lista de registros de tamaño constante.

| Sección | Tamaño | Descripción |
|---------|-------:|-------------|
| Cabecera | 3 bytes | Datos iniciales del paquete (función aún no identificada). |
| Inventario | N × 4 bytes | Lista de objetos del jugador. |

Representación:

```

+----------------------+
| Header (3 bytes)     |
+----------------------+
| Item 1 (4 bytes)     |
+----------------------+
| Item 2 (4 bytes)     |
+----------------------+
| Item 3 (4 bytes)     |
+----------------------+
| ...                  |
+----------------------+
| Item N (4 bytes)     |
+----------------------+

```

---

# Cabecera

La cabecera tiene un tamaño fijo de **3 bytes**.

Actualmente no se conoce la función exacta de estos valores.

| Offset | Tamaño | Tipo | Descripción |
|-------:|-------:|------|-------------|
| 0x00 | 1 byte | uint8 | unknown0 |
| 0x01 | 1 byte | uint8 | unknown1 |
| 0x02 | 1 byte | uint8 | unknown2 |

Ejemplo observado:

```

01 90 01

```

Estos bytes aparecen antes del primer registro del inventario.

---

# Lista de objetos

Después de la cabecera comienza la lista de objetos.

Cada registro ocupa exactamente **4 bytes**.

Estructura:

```

struct InventoryItem
{
uint16 itemId;
uint16 amount;
};

```

Cada campo utiliza formato:

- Tamaño: 2 bytes.
- Tipo: unsigned 16 bits.
- Endianness: Little Endian.

---

# Registro de objeto

| Campo | Tamaño | Tipo | Descripción |
|--------|-------:|------|-------------|
| Item ID | 2 bytes | uint16 | Identificador interno del objeto. |
| Cantidad | 2 bytes | uint16 | Cantidad disponible del objeto. |

Ejemplo:

```

09 02 00 3e

```

Interpretación:

```

ID:
09 02 → 0x0209 → 521

Cantidad:
00 3e → 0x003E → 62

```

---

# Ejemplo real

Fragmento del paquete:

```

09 02 00 3e
0c 03 00 53
0d 04 00 de

```

Interpretación:

| Hex | Item ID | Cantidad |
|-----|--------:|---------:|
| 0902 003e | 521 | 62 |
| 0c03 0053 | 780 | 83 |
| 0d04 00de | 1037 | 222 |

---

# Tamaño de un registro

Cada objeto ocupa:

| Campo | Bytes |
|--------|------:|
| Item ID | 2 |
| Cantidad | 2 |
| **Total** | **4 bytes** |

---

# Tamaño total del paquete

El tamaño del paquete se calcula como:

```

Tamaño = 3 + (CantidadDeObjetos × 4)

```

Donde:

- **3 bytes** corresponden a la cabecera.
- Cada objeto añade **4 bytes**.

---

# Funcionamiento del cliente

El cliente procesa el paquete de la siguiente manera:

```

leer header (3 bytes)

while (queden datos)
{
leer itemId;
leer amount;

```
inventory[itemId] = amount;
```

}

```

Después utiliza el `itemId` recibido para consultar la información almacenada localmente:

- Nombre.
- Icono.
- Calidad.
- Descripción.
- Categoría.
- Otros datos visuales.

El servidor no necesita enviar esa información.

---

# Características observadas

| Característica | Estado |
|----------------|--------|
| Cabecera fija | Sí |
| Tamaño de cabecera | 3 bytes |
| Registros de tamaño fijo | Sí |
| Tamaño de cada registro | 4 bytes |
| IDs de objetos | Sí |
| Cantidades | Sí |
| Nombres | No |
| Iconos | No |
| Descripciones | No |
| Datos visuales | No |

---

# Ventajas del diseño

| Ventaja | Explicación |
|----------|-------------|
| Compacto | Solo utiliza 4 bytes por objeto. |
| Rápido de procesar | Los registros tienen tamaño fijo. |
| Fácil sincronización | El cliente actualiza cantidades por ID. |
| Escalable | Permite manejar cientos o miles de objetos. |
| Bajo consumo de red | Solo transmite datos necesarios. |

---

# Flujo del protocolo

1. El servidor obtiene el inventario del jugador.
2. Genera la cabecera de 3 bytes.
3. Recorre los objetos disponibles.
4. Por cada objeto escribe:
   - Item ID (`uint16`)
   - Cantidad (`uint16`)
5. Envía el paquete al cliente.
6. El cliente actualiza el inventario usando los IDs recibidos.

---

# Estructura final

```

Header (3 bytes)

uint8 unknown0;
uint8 unknown1;
uint8 unknown2;

Repeated until end of packet:

uint16 itemId;
uint16 amount;

```

---

# Conclusión

El protocolo **1401** es una sincronización completa del inventario del jugador.

Su estructura consiste en una **cabecera fija de 3 bytes**, seguida por una lista de registros de **4 bytes** donde cada registro contiene:

- Un identificador de objeto (`uint16`).
- Una cantidad (`uint16`).

Todos los valores utilizan formato **Little Endian**.

La información visual de cada objeto permanece almacenada en el cliente, permitiendo que el protocolo sea pequeño, eficiente y rápido de procesar.
