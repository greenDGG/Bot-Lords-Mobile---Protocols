# Proto 2201 - Solicitar datos del mapa

## Descripción

El cliente envía `Proto=2201` (`_MSG_REQUEST_MAPDATA`) para solicitar los tiles del mapa
alrededor de una posición. El servidor responde con `Proto=2220`.

## Wire

| Proto | Wire | Cifrado |
|-------|------|---------|
| 2201 | — | Plano |

El body que se construye aquí va **detrás del seq de 4 bytes** que prepende
`sendCommandPacket(proto, payload, true)`; en el log se ve como
`[CMD] proto=2201 seq=<4B seq><45B payload>`.

## Payload (45 bytes fijos)

| Offset | Tamaño | Campo | Descripción |
|--------|--------|-------|-------------|
| 0 | 1 | count | Número de celdas de **ese** request (1..4) |
| 1 | 2×count | cells | Índices de celda como **uint16 LE** |
| resto | hasta 45 | reserved | Relleno en ceros → **longitud fija = 45 bytes** |

```
[count: 1B][count × uint16 LE][zeros …]   →  siempre 45 bytes
```

Ejemplos reales:

```
04 5200 5300 6200 6300 + 36 ceros (45B) → count=4, celdas [82, 83, 98, 99]
02 5300 6300          + 40 ceros (45B) → count=2, celdas [83, 99]
captura cliente: 04 ca01 cb01 da01 db01 + 36 ceros (45B) → celdas [458, 459, 474, 475]
```

La captura del cliente real (`docs/teories/a:366`) mide **45 bytes** y empieza por el
byte `04` (count) — es decir, el `plain` **no** incluye el seq: si el seq entrase, el
payload decodificado quedaría con bytes non-zero dentro del relleno (inválido).

### Varias llamadas por ventana (máx. 4 celdas)

El límite observado es de **4 celdas por llamada** (`MAX_CELLS_PER_REQUEST = 4`).
Si la selección devolviera más de 4, se trocea en tandas y cada tanda se manda como
**paquete 2201 independiente** con `REQUEST_COOLDOWN_MS = 3000` entre ellas:

```
t=0s → 2201 #1 (≤4 celdas)
t=3s → 2201 #2 (≤4 celdas)
t=6s → 2201 #3 …
```

Con la ventana 2×2 actual (4 celdas) **normalmente sale un único 2201**.
Cada 2201 recibe su propio 2220 (eco de sus celdas en la cabecera, ver proto 2220);
los tiles se acumulan incrementalmente en `bot.mapTiles`.
`requestMapData()` cancela las tandas pendientes de peticiones anteriores.

## Cálculo de la ventana

### 1. Coordenada → grilla

Fórmula experimental verificada:

```ts
gridX = Math.floor((X - 8) / 33);   // celdas de 33 de ancho, origen en X = 8
gridY = Math.floor((Y - 8) / 16);   // celdas de 16 de alto,  origen en Y = 8
```

Valores confirmados:

| X | gridX | | Y | gridY |
|--:|------:|-|--:|------:|
| 100 | 2 | | 9 | 0 |
| 107 | 3 | | 100 | 5 |
| 117 | 3 | | 200 | 12 |
| 140 | 4 | | 250 | 15 |
| 150 | 4 | | 300 | 18 |
| 160 | 4 | | 406 | 24 |
| 200 | 5 | | 420 | 25 |
| 208 | 6 | | 488 | 30 |

### 2. Grilla → índice

La grilla tiene **16 columnas**:

```ts
base = gridY * 16 + gridX;      // index = fila * 16 + columna
```

### 3. Ventana 2×2

```ts
cells = [base, base + 1, base + 16, base + 17];
```

```
┌──────────┬──────────┐
│   base   │ base + 1 │
├──────────┼──────────┤
│ base+16  │ base+17  │
└──────────┴──────────┘
```

### Ejemplos verificados

| X, Y | grid | base | ventana | payload |
|------|------|------|---------|---------|
| 100, 100 | (2, 5) | 82 | 82, 83, 98, 99 | `04 5200 5300 6200 6300` |
| 200, 100 | (5, 5) | 85 | 85, 86, 101, 102 | `04 5500 5600 6500 6600` |
| 100, 200 | (2, 12) | 194 | 194, 195, 210, 211 | `02 C200 C300` (solo parcial) |
| 100, 300 | (2, 18) | 290 | 290, 291, 306, 307 | `04 2201 2301 3201 3301` |
| 336, 410 | (9, 25) | 409 | 409, 410, 425, 426 | `04 9901 9A01 A901 AA01` |
| 242, 442 | (7, 27) | 439 | 439, 440, 455, 456 | `04 b701 b801 c701 c801` |

La última fila es exactamente la captura del cliente real citada en evidencia
y el servidor responde con un 2220 cuya cabecera eco'a esas mismas 4 celdas
(header 45 = `5 + 4×10`).

## Selección de celdas (count 4 vs count 2)

**La ventana calculada no es necesariamente la lista final enviada.** Se observaron
ambos comportamientos:

```
X=100, Y=100 → 04 5200 5300 6200 6300   (ventana completa: 82,83,98,99)
X=107, Y=100 → 02 5300 6300             (parcial: 83,99)
X=115, Y=100 → 04 5300 5400 6300 6400   (ventana completa: 83,84,99,100)
X=100, Y=200 → 02 C200 C300             (parcial: 194,195)
```

La regla exacta del cliente **no está determinada** (probablemente pide solo las
celdas que aún no tiene cargadas), así que vive en una función aparte:

```ts
selectCells(cells, known?)   // por defecto: ventana completa; nunca count=0
```

El cálculo de la ventana (`getMapWindow`) y la selección (`selectCells`) van
separados a propósito.

## Geometría de celdas

```
ancho de celda  = 33 unidades de mundo, primer borde en X = 8
alto de celda   = 16 unidades de mundo, primer borde en Y = 8
columnas        = 16  (0..15)
index           = gridY * 16 + gridX
```

Verificado con los valores de la tabla de confirmaciones (los límites de celda
caen exactos en X=107 → celda 3 = 8+33×3, X=140 → celda 4 = 8+33×4, etc.).

> **Corregido:** la fórmula antigua `gridX = floor(x / 32)` / ventana 3×3 con clamp
> de borde era incorrecta — con ella X=100 daba gridX=3 en vez de 2 y el bot pedía
> celdas equivocadas (por eso el servidor devolvía tiles de otra zona).

## Codificación de coordenadas (3 bytes)

Las coordenadas del mapa se codifican en 3 bytes a partir de `x` e `y` (en unidades de tile, no píxeles):

```
xi = floor(x / 2)
yi = floor(y / 2)
p  = (x & 1) | (y & 1)          ← paridad (bit 4 de byte2); x e y SIEMPRE la comparten

byte0 = (((yi >> 3) & 0x0F) << 4) | ((xi >> 4) & 0x0F)
byte1 = yi >> 7
byte2 = ((yi & 0x07) << 5) | (xi & 0x0F) | (p << 4)
```

El ID del tile se obtiene directamente de esos 3 bytes:
```
id = (byte0 << 16) | (byte1 << 8) | byte2
```

Para decodificar:
```
xiHigh = byte0 & 0x0F
xiLow  = byte2 & 0x0F
yiLow  = byte2 >> 5
yiMid  = (byte0 >> 4) & 0x0F
yiHigh = byte1

xi = (xiHigh << 4) | xiLow
yi = (yiHigh << 7) | (yiMid << 3) | yiLow
p  = (byte2 >> 4) & 1

x = xi * 2 + p
y = yi * 2 + p
```

> **Corregido:** antes `x = xi * 2` / `y = yi * 2` (siempre par) y se ignoraba `byte2 bit4`.
> Como resultado, todo tile en coordenada impar se mostraba con −1 en X e Y y, peor aún,
> **dos tiles distintos de la misma celda caían en la misma coordenada** (ej. (446,56) y
> (447,57) → ambos (446,56)). Verificado sobre 54.685 tiles de los logs: 337 celdas tenían
> las dos posiciones y el 36,6% de los tiles tenía paridad=1. El 2488 además mandaba `p=0`
> siempre, así que contra un bicho impar se apuntaba a la posición vecina.

### Ejemplo

El castillo principal con coordenadas hardcodeadas `db 00 eb`:
- byte0 = 0xdb = 1101_1011
- byte1 = 0x00 = 0000_0000
- byte2 = 0xeb = 1110_1011

Decodificando:
- xiHigh = 0x0b = 11
- xiLow  = 0x0b = 11  → xi = (11 << 4) | 11 = 187
- yiLow  = 111 = 7
- yiMid  = 0x0d = 13
- yiHigh = 0x00 = 0   → yi = (0 << 7) | (13 << 3) | 7 = 111
- p = (0xeb >> 4) & 1 = 0  → coordenada par

x = 187 * 2 + 0 = 374
y = 111 * 2 + 0 = 222

(Si `byte2` tuviera bit4 = 1 sería (375, 223).)

> El payload del **2201 NO usa esta codificación**: manda índices de celda u16 LE.
> La ID compacta de 3 bytes pertenece a los tiles (2220) y al proto 2202, y **no se
> toca** (está resuelta en `backend/src/models/map-coords.ts`).

## Notas

- El servidor acepta como máximo **4 celdas por llamada** (count=2 y count=4 observados; count=9 en una sola llamada NO). Esto es un *máximo observado*, no una regla demostrada: `MAX_CELLS_PER_REQUEST` puede subirse si se demuestra lo contrario.
- La ventana 2×2 siempre contiene la celda `base` (la que contiene la posición pedida).
- **Sin clamp de borde**: la spec observada manda `base+1`/`base+17` tal cual; no hay capturas de la columna 15 que permitan decidir si el cliente real desplaza la ventana (si X cae en col 15, `base+1` cae en la fila siguiente).
- El timeout de `openMapAndFindTarget` (15 s) sobra con un único paquete, pero se mantiene por si se vuelve a trocear en varias tandas.
- `gatherRegionQueryPacket(centerX, centerY, radius)` en `map-coords.ts` genera un payload diferente (región rectangular) y **no** se usa con 2201.
