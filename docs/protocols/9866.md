# Proto 9866 - Enviar tropa a buscar la carta (LUCKYCARD_MARCHING)

## Descripción

Comando **cliente → servidor**: manda la tropa a buscar la carta en un cofre
del mapa (especie **217**). Equivale al botón "buscar" del evento Carta de la
Suerte.

Regla del juego: **sólo puede haber UNA búsqueda por cuenta** hasta que la tropa
vuelve (ida + vuelta = 2× la duración que trae el `9867`).

Nombres del cliente de referencia: `_MSG_REQUEST_LUCKYCARD_MARCHING`
(`Protocol.cs:1716`).

## Wire

| Proto | Wire | Cifrado |
|-------|------|---------|
| 9866 | `0x268A` | Sí — DES / ECB (con seq) |

`sendCommandPacket(9866, coord, true)` → prepone seq de 4 bytes y cifra el body.
El paquete completo mide 11 bytes: `len(2) + proto(2) + seq(4) + coord(3)` →
header `0b008a26`.

## Payload (3 bytes, excluyendo el seq)

| Offset | Tamaño | Campo | Descripción |
|--------|--------|-------|-------------|
| 0-2 | 3 | coord | coordenada del cofre, misma codificación de 3 bytes que el resto del mapa ([`encodeCoord`](../../backend/src/models/map-coords.ts)) |

Mismo layout que el body del [`2202`](2202.md).

## Ejemplo real

```
[CMD] proto=9866 seq=12000000370265
      └seq=18┘└coord=370265┘ → (234, 566)
```

Respuesta esperada: [`9867`](9867.md) (status + duración de la búsqueda).

## Uso en el bot

```typescript
// backend/src/bot/commands/lucky-card.commands.ts
startLuckyCardSearch(bot, x, y);   // + waitMapProtoCooldown() (1 s)

// backend/src/bot/core/bot-instance.ts
runLuckyCardStep() → requestTileInfo() (2202) → sendLuckySearch() (9866)
```

Flujo completo dentro del bucle principal (`ActionRunner`):

1. `findLuckyChests()` arma los candidatos (cofres sin reclamar y fuera de
   backoff) ordenados por distancia al castillo: toma los
   `LUCKY_TILE_TRIES_PER_STEP = 3` más cercanos.
2. Se consultan **de a uno** con `2202` → `2220` (60 B):
   - `NOT` = sin reclamar → se manda el `9866` y el paso termina;
   - `YES` = ya reclamado **por esta cuenta** → se guarda en `claimedChests`
     (cache de sesión) y se pasa al **siguiente candidato** (no se corta el paso);
   - sin flag (`00000000`) → se cachea en `luckyChestBackoff` por
     `LUCKY_NO_FLAG_BACKOFF_MS` (10 min) y se pasa al siguiente candidato;
   - sin respuesta (5 s) → backoff de `LUCKY_CHEST_BACKOFF_MS` (60 s) y sigue.
   Si los 3 candidatos fallan, el paso devuelve `true` (igual llamó al juego) y
   el runner espera 30 s antes de reintentar.
3. `9866` al cofre → se ocupa el slot (`luckySearchBusyUntil`).
4. `9867` con la duración real → `busyUntil = ahora + 2×duración + margen`.
5. Cuando el `2220` (73 B) de la marcha muestra el retorno o vence el temporizador,
   se libera el slot (`releaseLuckySearch()`).

Si no queda ningún candidato (todos cacheados), el paso pide una ventana 2201
por ciclo (`refreshLuckyScan()`) para traer tiles nuevos.

## Notas

- Comparte el **cooldown de 1 s** con `2201`/`2202`/`2452`
  (`waitMapProtoCooldown()`); sin él el servidor contesta `2453` con `0x0e`
  (rate limit).
- Si el `9867` devuelve status ≠ 0, la marcha no sale y el bot desmarca el tile
  con backoff de `LUCKY_CHEST_BACKOFF_MS`.
- El bot sólo puede tener un `luckySearchTarget` a la vez: no manda otro `9866`
  hasta liberar el slot.
- Todavía no se observó un `9866` sin `9867` o con status de error en vivo.
