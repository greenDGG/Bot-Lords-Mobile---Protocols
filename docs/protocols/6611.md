# Proto 6611 — Agrupaciones activas a TORRES

## Dirección
IN (servidor → cliente)

## Descripción
Lista de agrupaciones activas contra **torres**. Equivalente al `2478` (castillos)
y al `7315` (fortalezas), pero con un layout propio.

**UN paquete = UNA agrupación** (body siempre de 87 bytes). Si hay N torres el
servidor manda **N paquetes separados** en ráfaga, no una lista. El parser viejo
recorría el body como si tuviera N entradas y producía entradas fantasma
(coords leídas dentro del nombre de gremio).

Llega en ráfaga junto con el `2477` y se **repite en cada refresco** (mismo
`timestamp` y líder, tropas actualizándose, slots repetidos).

## Payload (body de 87 B, `Len=91` = 4 de header de paquete + 87)

### Header de la entrada (bytes 0..5)

| Offset | Tamaño | Tipo | Descripción |
|--------|--------|------|-------------|
| 0 | 1 | uint8 | **lado**: `0` = propias del gremio, `1` = en contra |
| 1 | 1 | uint8 | **slot**: índice dentro de la lista de ese lado (0..N-1) |
| 2..4 | 3 | uint8 | `00` (sin usar) |
| 5 | 1 | uint8 | `00`/`01` (sin usar) |

`slot` sirve para hacer upsert: los paquetes se repiten en cada refresco y hay
que actualizar la entrada, no duplicarla. `slot == 0` marca **lote nuevo** de ese
lado → se borran las torres viejas de ese lado.

### Lado 0 — propias (`byte0 = 0`)

| Offset | Tamaño | Tipo | Descripción |
|--------|--------|------|-------------|
| 0..5 | 6 | — | header (lado + slot) |
| 6 | 4 | uint32 LE | timestamp de inicio (unix s) |
| 10 | 4 | uint32 | `00000000` (padding) |
| 14 | 4 | uint32 LE | tiempo restante (segundos, máx. observado 300) |
| 18 | 3 | bytes | **PointCode** → coordenadas (`decodeCoordBytes`) |
| 21 | 2 | bytes | AllyHead (low16 de un guild id; sin usar) |
| 23 | 13 | string | **rallyLeader** (null-padded) |
| 36 | 4 | uint32 LE | tropas actuales |
| 40 | 4 | uint32 LE | capacidad máxima |
| 44 | 1 | uint8 | tipo (3, 9, 11, 12… observados; sin usar) |
| 45 | 20 | string | gremio ⚠ semántica sin determinar |
| 65 | 9 | string | tag/gremio corto |
| 74 | 9 | uint8 | ceros |
| 83 | 4 | uint32 LE | misc (03, 0c, 0b…) |

### Lado 1 — en contra (`byte0 = 1`)

Mismos valores, **posición distinta** (el bloque de tropas adelanta):

| Offset | Tamaño | Tipo | Descripción |
|--------|--------|------|-------------|
| 0..5 | 6 | — | header (lado + slot) |
| 6 | 4 | uint32 LE | timestamp de inicio |
| 14 | 4 | uint32 LE | tiempo restante |
| 18 | 1 | uint8 | tipo |
| 19 | 4 | uint32 LE | tropas actuales |
| 23 | 4 | uint32 LE | capacidad (ver notas) |
| 27 | 3 | bytes | **PointCode** → coordenadas |
| 30 | 2 | bytes | AllyHead |
| 32 | 13 | string | **rallyLeader** (null-padded) |
| 45 | 9 | bytes | ⚠ sin determinar |
| 54 | 11 | bytes | gremio (parcialmente sobreescrito) |
| 65 | 9 | string | tag |
| 83 | 4 | uint32 LE | misc |

## Notas

- **Coordenadas**: mismo `PointCode` de 3 bytes que `2478`/`7315`. En torres el
  segundo byte **siempre** es 0 en las 40237 muestras → `y <= 255`.
- **Lados solapados**: la misma torre/líder aparece en ambas listas (p. ej.
  `Janni1318 1 (458,2)` existe como propia y como en contra) → la clave de
  agrupación del frontend incluye `side`.
- **Tropas**: `cur` crece en cada refresco (tropas que se van uniendo) y `max`
  es la capacidad. En 467/40237 muestras del lado 1 `cur > max` (ese campo no
  es la capacidad); en ese caso no se informa `max` para no mostrar
  "1.6M / 254K".
- **Gremio** (offset 45 lado 0): a veces trae mi gremio, a veces otro. La
  hipótesis es que es el gremio **defensor/objetivo**, no el del líder — sin
  confirmar y no se usa.
- El índice de selección (`WarEvent.index`, que manda el `2480`) **no** es el
  `slot`: lo recalcula `assignIndexes()` por menor tiempo restante.

## Comportamiento (`war-6611.ts` / `war-detector.ts`)

- `parse6611(payload)` → `Entry6611` (lado, slot, ts, timeRem, coord, líder,
  tropas).
- `apply6611(list, entry, iggId)` → upsert por `(lado, slot)`; con `slot == 0`
  limpia primero las torres de ese lado (lote nuevo).
- `2477` con un lado en 0 → se poda ese lado (`pruneTowerSide`). Los contadores
  **sí** incluyen las torres (propias == nº de paquetes lado 0 en cada ráfaga),
  pero van con desfase: sólo se poda cuando el contador llega a 0.
