# Proto 3633 - Mission Records

## Descripción

El proto 3633 contiene una cabecera de 4 bytes seguida de registros de misiones de 10 bytes cada uno. Cada registro representa una misión individual con su estado (normal, en espera, etc.).

> **Estado:** Análisis parcial. Cabecera sin identificar. Campo de 3 bytes sin identificar.

---

## Formato general

```
[ CABECERA: 4 bytes ][ REGISTRO 1: 10 bytes ][ REGISTRO 2: 10 bytes ][ ... ]
```

La cabecera es fija (4 bytes) y precede a todos los registros. Los registros se concatenan secuencialmente después de la cabecera.

---

## Cabecera (4 bytes)

| Offset | Tamaño | Campo | Descripción |
|--------|--------|-------|-------------|
| 0x00 | 4 | header | **Sin identificar** — cabecera global |

### Valores observados

| Hex | Notas |
|-----|-------|
| `09 00 13 00` | |
| `a0 11 30 02` | |
| `0b 02 13 00` | |

### Observaciones

- Los 4 bytes no forman parte de ningún registro de misión.
- **No está confirmado** qué representan.
- Podría ser: versión de protocolo, contadores, flags, o una combinación de estos.

---

## Tipos de registro

### 1. Normal (Mission Record)

| Offset | Tamaño | Campo | Descripción |
|--------|--------|-------|-------------|
| 0x00 | 2 | missionId | ID de la misión (uint16 LE) |
| 0x02 | 1 | level | Nivel de la misión (uint8) |
| 0x03 | 3 | unknown3 | **Sin identificar** — campo independiente |
| 0x06 | 4 | padding | Bytes de separación / relleno |

#### Valores conocidos de `unknown3`

| Hex | uint24 BE | uint24 LE | Notas |
|-----|-----------|-----------|-------|
| `d1 9e 6a` | 13737577 | 6956753 | Aparece en múltiples misiones/niveles |
| `f9 9e 6a` | 13802089 | 6957113 | |
| `cb 9e 6a` | 13753803 | 6956939 | |
| `b4 9e 6a` | 13723324 | 6956596 | |
| `0a 9f 6a` | 13832970 | 6957834 | |
| `06 9f 6a` | 13831942 | 6957830 | |
| `07 9f 6a` | 13832199 | 6957831 | |
| `05 9f 6a` | 13831685 | 6957829 | |
| `0f 9f 6a` | 13833999 | 6957839 | Nuevo en paquete completo |
| `10 9f 6a` | 13834256 | 6957840 | Nuevo en paquete completo |

#### Observaciones sobre `unknown3`

- El mismo missionId + level puede tener diferentes valores de `unknown3`.
- No es un identificador de misión.
- No es un contador secuencial simple.
- No es un timestamp (los valores no crecen monótonamente).
- **Hipótesis pendiente:** Podría ser un índice interno, referencia a tabla, o hash.

#### Ejemplo

```
0f 00 01 d1 9e 6a 00 00 00 00
│     │  │           │
│     │  │           └─ padding (4 bytes)
│     │  └─ unknown3: d1 9e 6a
│     └─ level: 01
└─ missionId: 0f 00 (uint16 LE = 15)
```

---

### 2. Waiting (Waiting Record — caso especial)

| Offset | Tamaño | Campo | Descripción |
|--------|--------|-------|-------------|
| 0x00 | 2 | status | `e9 03` = misión en espera |
| 0x02 | 4 | timestamp | Timestamp de disponibilidad |
| 0x06 | 4 | padding | Bytes de separación / relleno |

#### Identificación

El campo `status` tiene valor fijo `e9 03` (uint16 LE = 1001). Este valor se usa como marcador para distinguir registros de espera de registros normales.

> **Nota:** `e9 03` (1001) está en el rango alto. Los missionId observados en registros normales van de `0a 00` (10) a `2c 00` (44). Si algún missionId real fuera >= 1001, habría ambigüedad. Por ahora no se ha observado这种情况.

#### Ejemplo

```
e9 03 86 10 9f 6a 00 00 00 00
│     │              │
│     │              └─ padding (4 bytes)
│     └─ timestamp: 86 10 9f 6a
└─ status: e9 03 (waiting)
```

#### Timestamp

El campo de 4 bytes se interpreta como un timestamp o referencia temporal, pero **no está confirmado** qué formato usa exactamente.

Valores observados:

| Hex | uint32 LE | Posible interpretación |
|-----|-----------|------------------------|
| `86 10 9f 6a` | 1785664646 | Podría ser epoch |
| `7c 10 9f 6a` | 1785664636 | 10 segundos antes que el anterior |

La diferencia de 10 segundos entre los dos ejemplos sugiere que podría tratarse de un epoch en segundos.

---

## Detección de tipo

```
1. Leer primeros 4 bytes como cabecera.
2. A partir del byte 0x04, procesar registros de 10 en 10.
3. Para cada registro:
   Si los primeros 2 bytes == e9 03:
       → tipo: waiting
       → parsear como Waiting Record
   Si no:
       → tipo: normal
       → parsear como Normal Record
```

> **Advertencia:** Esta regla asume que `e9 03` nunca será un missionId válido. Si se descubre un missionId >= 1001, será necesario un mecanismo de desambiguación.

## Campos sin identificar

| Campo | Tamaño | Estado | Hipótesis |
|-------|--------|--------|-----------|
| header | 4 bytes | **Sin identificar** | Versión de protocolo, contadores, o flags |
| unknown3 | 3 bytes | **Sin identificar** | Índice interno, referencia a tabla, o hash |
| padding | 4 bytes | **Sin identificar** | Podría ser: timestamp de creación, checksum, o simplemente relleno |
| timestamp (waiting) | 4 bytes | **Sin identificar** | Posiblemente epoch en segundos |

---

## Conclusiones confirmadas

1. El paquete tiene una cabecera de 4 bytes antes de los registros.
2. Cada registro mide exactamente 10 bytes.
3. Los registros normales tienen: 2B missionId + 1B level + 3B unknown + 4B padding.
4. Los registros de espera tienen: 2B status (`e903`) + 4B timestamp + 4B padding.
5. `e903` se usa como marcador de "misión en espera".
6. El campo de 3 bytes es independiente del missionId y del level.
7. El mismo missionId + level puede tener diferentes valores en el campo de 3 bytes.

## Hipótesis pendientes

1. ¿Qué representa la cabecera de 4 bytes?
2. ¿Qué representa el campo de 3 bytes?
3. ¿Los 4 bytes de padding son realmente padding o contienen información?
4. ¿El timestamp de waiting es un epoch en segundos?
5. ¿Podría haber otros tipos de registro además de normal y waiting?
6. ¿Qué pasa si un missionId real es >= 1001 (rango de `e903`)?
